# Evan 发布与跨电脑开发

本文是跨电脑开发和 AI 接手项目时的发布基线。不要根据本机已有的 `release/` 或
`desktop-runtime/` 猜测当前版本；GitHub 的 `main`、版本 Tag 和 Release 才是依据。

## 1. 在其他电脑继续开发

```bash
git clone https://github.com/xgq947-ship-it/AI-Video-Canvas.git
cd AI-Video-Canvas
npm install
npm run setup
npm run setup:automation-runtime
npm test
npm start
```

- 开发环境使用 Node.js 22+、Python 3.11+，推荐 Python 3.12。
- `npm run setup:automation-runtime` 会在本机创建 Python 虚拟环境；浏览器使用系统正式版 Google Chrome。
- `.env`、项目素材、浏览器登录 profile 和 API 密钥不进入 Git，需要每台电脑单独配置。
- 普通用户不需要安装 Node、Python、FFmpeg、Codex CLI 或 Claude CLI，但必须安装正式版
  Google Chrome；只有使用可选 Codex 模型时才单独安装并登录最新版 Codex CLI。
- 不要提交 `node_modules/`、`release/`、`desktop-runtime/`、`dist/`、
  `server/python/.venv/`。

## 2. 正式版本发布

版本号以 `package.json` 为准，Tag 必须使用相同的 `vX.Y.Z`：

```bash
npm test
npm run build
git push origin main
git tag -a vX.Y.Z -m "Evan AI Video Canvas vX.Y.Z"
git push origin vX.Y.Z
```

推送 Tag 后，`.github/workflows/desktop-installers.yml` 会自动：

1. 在 macOS Apple Silicon runner 构建 DMG 和 ZIP。
2. 在 Windows x64 runner 构建 NSIS EXE。
3. 在两个平台分别运行完整回归测试并验收 Ops CLI、FFmpeg/FFprobe。
4. 将安装器和自动更新元数据写入对应的 GitHub Release。
5. Release 成功后删除本次 Actions 临时产物。

Actions Artifact 只用于构建 Job 之间传递文件，不是长期下载地址。其保留期设为 1 天，
用于发布失败时排查；成功发布后立即删除。长期文件只保留在 GitHub Release。

## 3. 安装文件与存储边界

- macOS 用户下载 `.dmg`；`.zip` 与 `latest-mac.yml` 可供 Electron 自动更新使用。
- Windows 用户下载 `-win-x64.exe`；`latest.yml` 和 blockmap 可供自动更新使用。
- Electron、独立 Python/Ops CLI、FFmpeg/FFprobe 内置；Chrome 不进入安装包，因此安装包
  比旧架构更小。
- Codex CLI 不进入安装包和 Git 依赖；安装版只包含 Evan 的 Skill 与队列桥接。用户在
  其他电脑使用 Codex 能力时，应安装当前 Codex CLI，并在应用设置中检测/选择和登录。
- 不要把安装包提交到 Git 历史，也不要把 Actions Artifact 当作 Release。
- Git 历史中已有的旧大文件不能靠普通删除减小；重写历史会要求所有协作者重新克隆，
  未经明确决定不要执行。

## 4. 发布故障处理

- 任一平台测试或构建失败时，不创建 Release，也不删除失败诊断所需的临时产物。
- 修复后先提交并推送 `main`，尚未公开的错误 Tag 可以移动到修复提交；已经公开使用的
  版本不得移动 Tag，应提升补丁版本并创建新 Tag。
- electron-builder 必须带 `--publish never`，由独立的发布 Job 统一创建 Release，避免
  两个平台并发发布和令牌缺失。
- 当前安装包尚未配置 Apple Developer ID/公证和 Windows Authenticode 签名，正式广泛
  分发前需要补齐签名凭证。

## 5. 发布一个新版本（用户能在应用内更新）

更新源就是 GitHub Release 本身：electron-builder 的 `build.publish` 指向本仓库，
打包时会把 `app-update.yml` 写进安装包，同时生成 `latest.yml` / `latest-mac.yml`
随 Release 一起发布。**不需要任何额外的服务器或配置文件。**

每次发新版按顺序做四件事：

1. 改 `package.json` 的 `version`（比如 `0.1.1` → `0.1.2`）。
2. 在 `CHANGELOG.json` **数组最前面**插入一条新记录，`version` 必须和上一步一致
   （`npm test` 会校验；对不上的话用户在「新功能」里会看到上一版的内容）。
3. 提交并推送 `main`。
4. 打 Tag 并推送，工作流会自动构建双平台安装包并创建 Release：

```bash
git tag v0.1.2 && git push origin v0.1.2
```

Release 创建完成后，已安装的用户：

- **Windows**：启动 10 秒后静默检查，设置 →「关于」里出现新版本，点「下载」→
  「重启并安装」即可。
- **macOS**：同样能检查到新版本，但只能点「前往下载」打开 Release 页手动下载覆盖。
  原因见下。

### 为什么 macOS 不能应用内安装

macOS 的安装步骤走系统原生的 Squirrel.Mac，它会校验运行中应用的代码签名。当前
工作流设置了 `CSC_IDENTITY_AUTO_DISCOVERY: 'false'`，mac 包未签名，**下载能成功但
安装必定失败**。所以 `electron/updater.js` 里 `supportsInAppInstall()` 只对
`win32` 返回 true，mac 一律走「跳转下载页」。

要开启 mac 应用内更新，需要：

1. 注册 Apple Developer Program（$99/年），拿到 Developer ID Application 证书。
2. 把证书与密码配成仓库 Secrets，在工作流里去掉 `CSC_IDENTITY_AUTO_DISCOVERY: 'false'`，
   并补上公证（notarize）步骤。
3. 改 `supportsInAppInstall()` 让 darwin 也返回 true，同时更新
   `test/desktopPackaging.test.mjs` 里对应的断言。

在没做完 1、2 之前不要改第 3 步，否则 mac 用户会卡在一个必定失败的安装流程里。

Windows 安装包同样未签名，能自动更新，但用户首次安装时 SmartScreen 会弹一次
「未知发布者」警告，需要点「更多信息 → 仍要运行」。配置 Authenticode 证书可消除。

## 6. AI 接手时先检查

1. 阅读 `README.md`、`docs/项目说明.md`、`docs/development.md` 和本文。
2. 检查 `git status`，不得覆盖用户未提交的修改。
3. 以 `package.json`、工作流和测试为事实来源，不使用旧聊天里的分支名或 commit。
4. 修改桌面发布流程后运行 `node --test test/desktopPackaging.test.mjs` 和完整
   `npm test`。
5. 只有用户明确要求发布时，才允许推送版本 Tag 或修改 GitHub Release。
