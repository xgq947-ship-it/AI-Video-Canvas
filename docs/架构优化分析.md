## 0. 先说结论：哪些地方已经很好，不用再动

这个项目的渲染热路径**已经被认真优化过**，不要重复劳动：

- `src/hooks/useNodeDragging.ts` — 指针事件按 rAF 合帧，且在 `pointerup` 时同步
  flush 最后一帧（考虑了 Electron `backgroundThrottling`）。
- `src/components/canvas/CanvasNode.tsx:680` — `React.memo` + `App.tsx:2600` 起的
  稳定 props 处理：ref 转发回调、`allNodes` 按节点类型选择性下发、
  `nodeConnectedReferences` 手写依赖缓存。
- `src/utils/autoSaveScheduler.js` — 定时器只创建一次，用 `getState` 读最新状态，
  避免了"每帧重置计时器导致自动保存永不触发"的经典坑。
- `src/components/LazyVideo.tsx` + `useLazyVisibility.ts` — 视口外的 `<video>` 会
  卸载并在 5s 后释放解码器。

## 一、流畅度（运行性能）

### P2 — `canvasMediaSignature` 在每个拖拽帧做全画布字符串拼接 `[需实测]`

`src/App.tsx:127` 定义、`src/App.tsx:507` 在一个 `[nodes, workflowId]` 的 effect
里调用。它对**每个节点**拼接 6 个字段，并对每个 storyboard 节点的**每个分镜**再
拼 3 个字段，最后 join 成一个巨型字符串。

由于依赖是 `nodes`，拖动一个节点时它每帧都跑一遍，代价随项目规模线性增长——
正好符合"项目一大就发涩"的现象。而它的**唯一目的**是检测"是否出现了新的媒体
产物"，与节点坐标完全无关。

**修法（二选一）**：

1. 廉价前置门控——先比较一个 O(n) 的轻量计数（有 `resultUrl` 的节点数 +
   `videoMerge.outputUrl` 数 + 已完成分镜数），计数不变就直接 return，不拼字符串。
2. 更彻底——媒体产物的写入点是已知的（`useGeneration.ts`、分镜回调等），改为在
   这些位置显式调用 `requestMediaSave()`，彻底移除这个"轮询式 diff"effect。

方案 2 更干净，但要盘点所有写入点；方案 1 十行内可完成，建议先做 1。

**同类小问题**：`src/hooks/useVideoFrameExtraction.ts:56-67` 是第二个挂在
`[nodes]` 上的 effect，每次变化都 `new Set(nodes.map(...))` 加一次数组拷贝。
量级比 P2 小得多，顺手一起处理即可。

### P3 — 画布节点没有视口剔除（DOM 层面） `[需实测，但方向确定]`

`src/App.tsx:2961` 是 `{nodes.map(node => <CanvasNode ... />)}`，**没有任何视口
过滤**。`LazyVideo` 解决了媒体解码器的问题，但每个节点的 DOM 子树仍然全部挂载，
而 `NodeControls.tsx` 有 **1699 行**——即使节点在屏幕外几千像素，它的整棵控件
子树依然存在于 DOM 中并参与 React 协调。

**修法**：在 `nodes.map` 前按视口矩形做剔除，屏幕外节点渲染为一个固定尺寸占位
`<div>`（保持 minimap 和包围盒计算不受影响）。仓库里 `src/utils/canvasRect.ts`
和 `shared/canvasCoords.js` 的 `computeFitViewport` 已提供所需几何工具。

注意保留一圈 margin（建议 1~2 屏），避免拖拽边缘时节点闪烁。这是节点数上百后
收益最大的一项，但改动面也最大——建议排在 P1/P2 之后。

### P5 — 批量生成会触发 2N 次全量落盘（两条独立路径） `[代码可证]`

这里有**两个**互相叠加的问题，必须一起修：

**(a) 媒体产物路径 —— 0ms 去抖形同虚设。**
`src/App.tsx:517` 用 `setTimeout(..., 0)` 加 `mediaSaveTimerRef` 做去抖，但 0ms
只能合并**同一个 tick 内**的变更。10 个分镜在几十秒里陆续产出 = 10 次完整画布
序列化 + 写盘。

**(b) LOADING 计数路径 —— 完全没有去抖。**
`src/App.tsx:484-489`：

```js
const currentLoadingCount = nodes.filter(n => n.status === NodeStatus.LOADING).length;
if (currentLoadingCount > lastLoadingCountRef.current) {
  handleSaveWithTracking();   // 没有 setTimeout，没有 ref 门控
}
```

只要 LOADING 节点数**增加**就立刻同步触发一次全量保存，连 (a) 那点聊胜于无的
去抖都没有。

火柴人批量生成同时命中两条：N 个分镜进入 LOADING → N 次保存；N 个分镜产出媒体
→ 再 N 次保存。**总计约 2N 次全量画布序列化 + 写盘**，全在主线程上。这正是
"批量生成时界面发顿"的直接原因。

**修法**：把两条路径合并到**同一个** 800~1500ms 的去抖器里（并在 `beforeunload`
和项目切换时 flush）。既保住"崩溃可恢复"的初衷，也把批量场景压缩到一两次写盘。

> ⚠️ 此项触及持久化逻辑，按 `AGENTS.md` 要求必须补回归测试（`test/` 下已有
> `autoSaveScheduler` 相关用例可参照）。

## 二、交互友好度（UX）

### U1 — 核心生成任务无法取消 `[代码可证]`

服务端对**周边**任务都实现了取消：

- `server/routes/render.js:79`
- `server/routes/generation.js:109`（product-scene）
- `server/routes/stickman-director.js:74`（merge）

但**主生成链路**（`useGeneration.ts` 走的图/视频生成）没有取消端点，
`src/components/canvas/NodeControls.tsx`（1699 行）里搜不到任何"取消"字样。
已核对：`src/hooks/useGeneration.ts` 和 `src/services/generationService.ts` 里
**也没有任何 `AbortController` / `signal`**，即前端连中断请求的能力都没有——
不是"有能力但没露出来"，而是整条链路都缺。

视频生成动辄几分钟。用户选错模型或写错提示词后，唯一的选择是等它跑完、或删掉
节点（而后端任务仍在消耗配额继续跑）。这是当前最伤体验的一处缺口。

**修法**：`server/services/operationCancelled.js` 已经存在，说明取消语义在服务端
是有基础设施的。补一个 `POST /api/generation/:nodeId/cancel`，前端在 LOADING 态
的节点上露出取消按钮。

### U2 — 生成中只有一个转圈，没有进度、阶段或已用时长 `[代码可证]`

`NodeContent.tsx:137` 和 `:231` 的 LOADING 态就是一个 `<Loader2 className="animate-spin">`。

对比之下，渲染节点（`MangaNode`）能显示 `renderStage` / `renderProgress`——**同一个
应用里，两类任务的反馈详尽程度差距很大**。

更可惜的是：`generationStartTime` 这个字段**已经存在并被正确写入**
（`types.ts:193`、`useGeneration.ts:153`），但在整个 UI 层没有任何一处读它来显示
已用时长。

**修法（成本递增）**：

1. 立刻可做——在 LOADING 态显示 `已生成 1:24`，数据现成，只差一个渲染。
2. 中期——生成链路补上 stage 字段（排队中 / 提交中 / 生成中 / 下载中），与
   render 的反馈粒度对齐。

第 1 步几乎零成本，却直接回答了用户最焦虑的问题："它到底是在跑，还是卡死了？"

### U3 — 错误提示会自动消失，且不带重试入口 `[代码可证]`

`src/hooks/useToasts.ts` 的 tone 只有 `'info' | 'error'`，错误 toast 在
`App.tsx:555`（`useGeneration` 的 `notify`）里设的是 6500ms 后自动消失。
生成失败往往发生在用户切走去做别的事
的时候——回来时提示已经没了，只剩节点上一个红色状态。

Toast 也不支持任何操作按钮，所以没法做"失败了 → 点这里重试"。

**修法**：错误 tone 改为不自动消失（必须手动关闭），并给 `Toast` 加一个可选的
`action: { label, onClick }` 字段。`ToastStack.tsx` 结构简单，改动很小。

**值得表扬的反例**：节点内的错误态处理得相当好——`NodeContent.tsx:236-260` 会
识别"已扣费"的失败并**刻意隐藏重试按钮**，提示用户先去平台历史确认，避免重复
扣费。这个细节做得比大多数同类产品都细，建议把同样的克制感延伸到 toast 层。

### U4 — 快捷键覆盖不错，但缺少发现入口 `[代码可证]`

`useKeyboardShortcuts.ts` 实现了复制/粘贴/复制副本/删除/撤销重做/成组/连线/
生成/自动排列/缩放/fit/空格平移——覆盖面相当完整。

但应用里没有任何快捷键速查表或提示浮层，用户基本发现不了。一个 `?` 键唤出的
快捷键面板是极低成本、高感知收益的改动。

顺带两个小问题：

- `handlePaste`（`useKeyboardShortcuts.ts:73`）用
  `Date.now().toString() + Math.random()...` 生成 ID，而同文件的
  `handleDuplicate` 用的是 `crypto.randomUUID()`。统一成后者。

- **fit 视口存在三套实现，其中一套绕开了有测试覆盖的共享函数。**
  `shared/canvasCoords.js:99` 的 `computeFitViewport` 有完整单测
  （`test/canvasCoords.test.mjs`，6 个用例），`App.tsx:949` 和
  `useWorkflow.ts:208` 都正确调用它；但 `useKeyboardShortcuts.ts:126` 的
  `fitCanvas`（快捷键 fit）是**手写的第三套**，有自己的 padding 计算和硬编码的
  `365 × 480` 节点尺寸。

  这里要小心：`DEFAULT_NODE_WIDTH = 365` 与硬编码值一致，但
  **`DEFAULT_NODE_HEIGHT = 300`，和硬编码的 480 对不上**。所以*不能*简单地把
  480 换成常量——那会低估节点高度，让 fit 反而更差。正确做法是先确定节点的真实
  渲染高度到底该按哪个值算，再把 `fitCanvas` 改为调用 `computeFitViewport`。
  真正的问题是这套逻辑分了三份且彼此不一致，常量只是症状。

## 三、架构（可维护性 — 与上面的运行时问题分开看）

这部分**不影响运行流畅度**，是长期开发效率问题。是否处理取决于你更在意哪一边。

| 文件 | 行数 | 问题 |

**最容易切的一刀是 `server/index.js`**：`app.use('/api', generationRoutes)` 这套
模式已经建立，只需把剩下的内联路由按域搬进 `server/routes/`：

- `library.js`（`:399` upload / `:462` create / `:588` list / `:605` delete）
- `projects.js`（`:696` 起，含 assets 子路由至 `:1000` 前后）
- `trash.js`（`:1015` – `:1100` 前后）
- `workflows.js`（`:1104` – `:1360` 前后，含 public-workflows）
- `browser.js`（`:1395` 起的 browser-sessions / browser open）

（行号为起始锚点，区间为约数——搬运前请以实际 `app.get/post/...` 边界为准。）

这是纯搬运、行为不变、风险极低，能让 index.js 回到 300 行以内。

**`App.tsx` 的拆分**要谨慎：它的复杂度大部分来自跨节点类型的编排逻辑（火柴人
导演、视频分析、产品场景），硬拆容易把已经调好的 memo 稳定性破坏掉。建议的边界
是按**领域**抽 hook（`useStickmanOrchestration`、`useVideoAnalysisOrchestration`），
而不是按"UI / 逻辑"横切。

## 五、诚实的边界

- 全部结论基于**静态阅读**。P1/P4/P5/U1/U2/U3/U4 标注为 `[代码可证]`，读代码即可
  确认；P2/P3 的**方向**确定，但实际收益需要在真实规模的项目上用 React DevTools
  Profiler 和 Chrome Performance 面板实测才能定量。
- 具体地：「P1 每帧重建定时器」「P5 两条路径共约 2N 次保存」「U1 全链路无
  AbortController」「U4 三套 fit 实现且节点高度 300≠480」都是逐行核对过的事实；
  而「视口剔除能带来多少帧率提升」「素材网格换 LazyVideo 省多少内存」是推断，
  需要实测。
- 当前工作区有 20 个已修改文件和 5 个新增文件（含 `projectImport`、
  `projectMediaRecovery` 及其测试）。上述建议均未与这些改动重叠，但落地前建议先
  让这批改动进入一个稳定状态。
- 我没有运行 `npm test`，也没有启动应用实测。如果需要，可以先跑一遍基线。
