# Video Remix 关键帧工作流

关键帧层位于 Prompt 确认与图生视频之间。它复用现有图片 Provider、项目持久化和
`/api/generate-image` 路由，不新增运行时依赖，也不会在关键帧完成后自动生成视频。

## 生成计划

系统根据每个 Shot 已分析的 `motionComplexity` 生成稳定计划：

- `simple`：Start
- `medium`：Start、End
- `complex`：Start、Middle、End

这只控制生成数量，不减少分析阶段保存的五点参考帧。Start、Middle、End 会分别匹配
最接近的已提取原参考帧；缺少精确位置时按固定顺序回退。

每个关键帧使用独立 `imagePrompt`，再补充该时刻的静态状态和节奏。Start/End 使用
Shot 连续性状态，Middle 使用当时正在发生的主体动作与道具交互。Prompt 明确禁止动作
轨迹、分镜拼图、字幕和时间标记，并继续锁定人物数量与位置、朝向、景别、构图、机位、
透视、场景功能区及道具位置。

## 参考图优先级

Provider 的参考图数量有限，提交前按以下顺序去重和截取：

1. 当前 Shot 使用的替换人物、替换 Look、替换场景和替换道具；
2. 当前 Start/Middle/End 对应的原视频参考帧；
3. 未替换的 Look、人物、场景和道具参考图。

只有 Look 被替换时，替换 Look 在最前，原参考帧仍排在旧人物身份图之前。这样小上限
模型不会因旧资产挤占名额而丢失新造型或原构图。

## 队列、失败与恢复

前端批量队列并发上限为 2，同时继续经过现有 Provider 调度器。每帧独立保存状态、尝试
次数、模型参数、参考图、Prompt 和输入哈希：

- 单帧失败不清空其他成功结果；
- 可重试失败支持批量或单帧重试；
- 明确不可重试的错误不进入自动批量重试，用户处理登录等原因后仍可单帧重试；
- 请求可能已提交但返回未知时标记 `retryBlocked`，防止自动重复扣费；用户核对平台历史
  后可明确点击“核对后重试”；
- 应用中断后，超过 20 分钟仍为 `generating` 的任务恢复为安全可重试；
- 旧异步结果必须匹配 `inputHash`，否则不能覆盖新 Prompt 或新模型的结果。

生成结果由现有图片生成路由写入当前项目素材目录，项目 JSON 保存可恢复的队列状态。
输入未变化时复用已生成结果；修改图片模型、画幅、分辨率、Prompt 或上游资产会使对应
缓存与所有下游视频、成片结果失效。

## 人工确认门

关键帧页以 Shot Grid 同时显示“原参考”和“新关键帧”，支持生成全部未完成项、只重试
失败项、单帧重新生成、编辑 Prompt、单帧确认及全部确认。

只有所有计划内关键帧都有结果并由用户确认后，`keyframeReview.confirmed` 才会置为
`true`。视频生成阶段必须读取该确认门；关键帧成功本身不会触发图生视频。

未登录 Gemini 不影响关键帧计划、Prompt 编辑、缓存恢复、界面确认、测试或本地媒体
处理。只有用户选择 Gemini Web（或其他需要网页登录的 Provider）并实际发起生成时，
才需要对应登录态；错误会保留在当前关键帧，处理登录后可继续。
